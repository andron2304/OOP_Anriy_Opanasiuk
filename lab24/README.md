# IndependentWork24

Консольний проєкт для лабораторної роботи №24.

## Що реалізовано

- Інтеграція структурних патернів:
  - `Composite`: `Product`, `ProductBundle`
  - `Decorator`: `DiscountDecorator`, `TaxDecorator`
  - `Proxy`: `LoggingPriceCalculatorProxy`
- Тести перевіряють інтеграцію, негативні кейси та поведінку у випадках з декоратором.
- У Main додано базове порівняння продуктивності між простим та проксі/декорованим сценаріями.

## Як запустити

```bash
cd IndependentWork24
dotnet run
```

## Що протестовано

- Розрахунок значення простого продукту.
- Розрахунок значення групи продуктів через Composite.
- Застосування знижки та податку через Decorator.
- Проксі логування на прикладі обчислення ціни.
- Негативний випадок: виклик Calculate з null-об'єктом.
- Усі тести пройшли успішно: `4` тести, `0` провалів.

## Контрольні питання та відповіді

1. **Які структурні патерни інтегровані в цьому рішенні?**
   - **Composite** (`Product`, `ProductBundle`): дозволяє створювати дерево об'єктів, де листи та гілки мають одинаковий інтерфейс `IComponent`. Використано для представлення товарів та їхніх наборів.
   - **Decorator** (`DiscountDecorator`, `TaxDecorator`): динамічно додає відповідальність до об'єкта без зміни його коду. Дозволяє послідовно застосовувати знижки та податки.
   - **Proxy** (`LoggingPriceCalculatorProxy`): контролює доступ до іншого об'єкта (`SimplePriceCalculator`), додаючи логування та контроль виконання без зміни інтерфейсу калькулятора.

2. **Яка роль Proxy у інтеграції з Composite та Decorator?**
   - Proxy обгортає калькулятор ціни й логує всі операції розрахунку. Таким чином, Proxy дозволяє прозоро (без зміни клієнтського коду) додавати моніторинг та аудит до системи розрахунку.
   - При обчисленні ціни Proxy викликає внутрішній калькулятор, який отримує об'єкт, потенційно складений через Composite та прикрашений через Decorator.
   - Це дозволяє розділити відповідальність: бізнес-логіка залишається в Composite/Decorator, а керування доступом і логування – в Proxy.

3. **Які компроміси продуктивності виникають при використанні Decorator та Proxy?**
   - **Decorator**: кожен рівень декоратора додає виклик методу в стек. При глибокій ланцюзі декораторів (наприклад, знижка → податок → ще щось) збільшується кількість функціональних викликів і обчислень. На практиці для невеликої кількості декораторів (2–3) вплив мінімальний.
   - **Proxy**: додатковий рівень непрямого виклику означає, що виклик методу проходить через проксі перед тим, як потрапити в справжній об'єкт. Логування та інші операції проксі додають обробку перед основною роботою.
   - **Висновок**: обидва патерни мають мінімальний вплив на продуктивність для типових сценаріїв, але при масштабуванні (мільйони операцій) варто враховувати накладні витрати інтерпретації та виклику методів. Вибір гнучкості кода над максимальною швидкістю є виправданим компромісом.
