# Стратегія тестування (Test Strategy)

## 1. Критичні сценарії
- Створення сутностей із валідацією (негативні суми, неправильні стани).
- Процес зміни статусів (з "New" на "Paid").
- Збереження та завантаження стану системи у файл.

## 2. Складні для тестування зони
- Файловий I/O: тестується через виділення `IOrderRepository` (Dependency Inversion). Для інтеграційних тестів використовуються тимчасові файли (`Path.GetTempFileName()`).

## 3. Mocks vs Інтеграція
- **Mocks (Moq):** Використовуються в Unit-тестах для `OrderService`, щоб ізолювати бізнес-логіку від файлової системи.
- **Реальна інтеграція:** Використовується в Integration-тестах для перевірки `JsonOrderRepository` та повного циклу життя програми.

## 4. Негативні сценарії
- Пошкоджений JSON файл (перевірено інтеграційним тестом).
- Відсутній файл або порожній файл (перевірено).
- Помилки доступу до диску (I/O exceptions перехоплюються і конвертуються у `DomainException`).

# Інструкція з тестування

## Запуск тестів та генерація Coverage
Щоб запустити тести локально з перевіркою покриття, виконайте команду:
`dotnet test /p:CollectCoverage=true /p:CoverletOutputFormat=opencover`

## Що покрито тестами:
1. **Unit-тести (~20 кейсів через Theory):**
   - Валідація моделей (Order).
   - Бізнес-правила зміни статусів.
   - Поведінка сервісів із замоканими репозиторіями.
2. **Integration-тести (8 кейсів):**
   - Збереження у тимчасові файли.
   - Завантаження з файлів.
   - Відновлення після пошкодження даних (Fault Handling).

# Звіт по Ітерації 3

## Що було зроблено
1. **Рефакторинг:** Виділено `IOrderRepository` для створення seams (швів) для тестування.
2. **Тестування:** Написано >20 юніт-тестів (з використанням `Theory`) та 8 інтеграційних тестів.
